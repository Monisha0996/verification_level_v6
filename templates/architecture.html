How the services connect

1. Client registers → CRM creates client_id and mock applicant_id
↓
2. Client submits dummy card evidence → mock Sumsub action → admin approves/rejects
↓
3. CRM stores approved verification + masked card references
↓
4. Deposit created → mock Ottu session → hosted checkout simulator
↓
5. Successful mock PSP result → create token → link token to approved card
↓
6. Next deposit with same saved card → reuse approved token binding → no second evidence capture
↓
7. CRM records demo MT5 credit only after mock payment success

Production boundaries

Sumsub: Upload card evidence through its hosted SDK; use authenticated applicant-action APIs and verified webhooks. Ottu: Generate a real checkout URL with your backend; let its hosted page and PSP receive payment credentials; verify payment webhooks server-side. CRM: Persist only masked metadata, approved status, external IDs and protected PSP token references.

Identity binding caveat: BIN + last four + expiry is not guaranteed unique. Before skipping a future ownership check, confirm a secure link between the Sumsub-verified card and the saved PSP token or fingerprint. This demo assumes that binding as a teaching simplification.
