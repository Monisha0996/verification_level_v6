Integration notes & recommended order

DEMO ONLY: This application does not connect to the live Sumsub, Ottu, PSP, or MT5 systems. Use fabricated names and card images only. Never enter real PAN, CVV, identity documents or client card images.

Updated two-deposit client journey

  1. Upload dummy card image in the Sumsub simulation. Admin approves its verification record.
  2. First deposit: enter fictional cardholder, BIN, last 4 and expiry inside the mock Ottu page. CRM checks these against the approved mock verification.
  3. If the mock payment succeeds, store the synthetic gateway token against the CRM card record.
  4. Second deposit: Ottu mock shows a Previously used · Sumsub verified saved card. The saved-token path skips card re-entry and repeated evidence upload.
  5. If the first checkout details mismatch, hold the request and do not credit MT5. The comparison is demonstrative only; real systems need robust PSP-to-Sumsub binding.

1. Recommended implementation order

  1. KYC: Complete real Sumsub KYC; retain applicantId against the CRM client profile. The demo generates fictional IDs.
  2. Card verification: Trigger Sumsub Payment Method Check / applicant action; use its SDK to collect card evidence directly in Sumsub, not on the AZM server. Receive and validate verification webhooks and retrieve check details.
  3. Secure card binding: Record Sumsub applicantId, actionId, check result and allowed masked metadata. Obtain a robust way to establish the payment token identifies the same verified card. BIN + last four is not unique proof.
  4. Ottu checkout: Create a hosted checkout session server-side; user enters card details only in the real Ottu/PSP payment flow. Apply payment authorization, any 3DS requirements, and necessary approvals.
  5. Token & reconciliation: If supported and enabled, Ottu/PSP provides a saved-card token. The CRM stores a protected token reference bound to the approved card, and validates authenticated payment webhooks and final status.
  6. MT5 credit: Credit only after confirmed payment success, satisfied ownership checks and compliance controls, with idempotency and audit logs.
  7. Repeat deposit: Match a saved token to the currently approved binding and apply current risk checks. Skip repeat ownership capture only when authorised by policy; recheck new/unlinked cards.

2. What happens to card images and data?

Demo: dummy images are uploaded locally and are admin-viewable. This is solely a training simulation.

Production: Sumsub's SDK should collect real evidence in its environment. Keep only permitted masked metadata and verification identifiers in AZM CRM; do not store real card photographs, CVV or full PAN in this Flask application. Confirm Sumsub's assigned storage region and data-processing arrangements in writing.

Retention: Based on Sumsub's supplied reply, its default retention is during the active agreement, followed by a 30-day export opportunity after termination. This does not establish automatic deletion on day 31. Obtain written specifics for evidence images, extracted data, backups and deletion exceptions.

Note: A masked card number is not a primary key, and a Sumsub action ID is not proof of the same card being presented at checkout.

4. Vendor confirmations needed before live use

  • Sumsub: card-ownership evidence mechanism, fields returned, persistent payment-method ID/fingerprint availability, images and extracted-data retention, actual data residency.
  • Ottu / PSP: saved token creation and vault location, whether token is known before payment or only after, same-card binding mechanisms, gateway portability, authentication and webhook verification.
  • Silicon Fort / CRM: token encryption and access controls, customer-to-card binding, webhook reconciliation, exceptional handling, and prevention of premature MT5 credit.
